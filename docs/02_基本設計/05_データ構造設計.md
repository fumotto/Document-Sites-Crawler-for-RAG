# 05_データ構造設計

## 設計方針

- データ構造は責務ごとに分離し、差分更新・ビルド・出力が互いに独立して動作できる構成とする。（保守性・拡張性を高めるため）
- DTOはすべて `@dataclass(frozen=True)` による Immutable オブジェクトとする。（途中で内容が変更されることを防ぐため）
- DTOは1ファイル1クラスを原則とし、責務ごとに `models/` パッケージへ配置する。（保守性・レビュー性を高めるため）
- 取得できない値は `Optional`（`None`）を許容する設計とする。（取得失敗時のNullableフィールドを安全に扱うため）
- DTOはデータのみを保持し、JSON変換処理は Mapper クラスへ分離する。（責務分離を徹底するため）
- 日時フィールドはすべて ISO8601（タイムゾーン付き）で統一する。MapperがJSONとの相互変換時にシリアライズ／デシリアライズを担う。
- `manifest.json` は差分更新に必要な最小限の情報のみを保持する。（毎回高速に読み込めるようにするため）
- `metadata/` 配下にはビルド・分析・NotebookLM向け出力に必要な詳細情報を保持する。（差分更新処理を軽量化するため）
- `{page_hash}` は正規化後URLのSHA-256値を用いる。（本文更新時もファイル名を維持し、キャッシュを再利用するため）
- `manifest.json` は正規化URLをキーとした辞書構造とする。（高速検索を実現するため）
- 各JSONファイルは将来の拡張を考慮し、後方互換性を意識した構造とする。（項目追加を容易にするため）
- `duplicate`（重複判定）は `manifest.json` には保持しない。BuilderがビルドのたびにMetadataの `content_sha256` を全件照合して毎回判定する。（「manifestはビルド時に使わない」という設計方針との一貫性を保つため）
- `manifest.json` の更新はマージ更新とする。（一時的な失敗時に過去の成功情報を失わないようにするため）

## manifest.json

### 役割

- 差分更新判定
- キャッシュ管理
- HTTPキャッシュ制御
- 再開（Resume）処理

**ビルド時には利用しない。**

### 格納形式

```json
{
  "version": "1",
  "pages": {
    "<normalized_url>": {
      "page_hash": "sha256_of_normalized_url",
      "etag": "\"abc123\"",
      "last_modified": "Tue, 01 Jul 2026 00:00:00 GMT",
      "sitemap_lastmod": "2026-06-30T12:00:00+09:00",
      "content_sha256": "sha256_of_body",
      "last_crawled": "2026-06-30T21:30:45+09:00",
      "crawl_result": "SUCCESS"
    }
  }
}
```

### フィールド

| フィールド | 型 | Nullable | 説明 |
|---|---|---|---|
| `version` | `str` | No | manifest.jsonのスキーマバージョン。現在値は `"1"` |
| `page_hash` | `str` | No | 正規化URLから生成したSHA-256。URLから機械的に算出できるため常に存在する |
| `etag` | `str` | Yes | HTTP ETag。サーバーが返さない場合は `null` |
| `last_modified` | `str` | Yes | HTTP Last-Modified。サーバーが返さない場合は `null` |
| `sitemap_lastmod` | `str` | Yes | sitemapに記載された `lastmod`。未記載の場合は `null` |
| `content_sha256` | `str` | Yes | 本文SHA-256。取得失敗時は `null` |
| `last_crawled` | `str` | No | 最終クロール試行日時（ISO8601 タイムゾーン付き） |
| `crawl_result` | `str` | No | クロール結果種別（下記参照） |

### CrawlResult 定義

| 値 | 説明 |
|---|---|
| `SUCCESS` | 200 OK。コンテンツ取得成功 |
| `NOT_MODIFIED` | 304 Not Modified。本文未変更（manifest更新は行わない） |
| `NOT_FOUND` | 404。ページが存在しない |
| `ROBOTS_DENIED` | robots.txtにより取得を禁止されている |
| `NETWORK_ERROR` | 接続エラー・DNSエラー等 |
| `TIMEOUT` | タイムアウト |
| `SERVER_ERROR` | 5xx系エラー |
| `TOO_MANY_REQUESTS` | 429 Too Many Requests |

> `NOT_MODIFIED` はmanifestを更新する必要がないため、実際にmanifestへ書き込まれることはない。前回の `crawl_result: SUCCESS` がそのまま保持される。

### マージ更新ルール

manifest.jsonの更新は **マージ更新** とする。一時的な失敗時に、過去の成功情報（`page_hash` / `etag` / `last_modified` / `content_sha256`）を上書きしてデータロスが起きないようにする。

| crawl_result | 更新する項目 | 保持する項目 |
|---|---|---|
| `SUCCESS` | 全フィールドを更新 | — |
| `NETWORK_ERROR` / `TIMEOUT` / `SERVER_ERROR` / `TOO_MANY_REQUESTS` | `last_crawled`、`crawl_result` | `page_hash`、`etag`、`last_modified`、`sitemap_lastmod`、`content_sha256` |
| `NOT_FOUND` / `ROBOTS_DENIED` | `last_crawled`、`crawl_result` | `page_hash`、`etag`、`last_modified`、`sitemap_lastmod`、`content_sha256` |

### 削除・404ページの扱い

「sitemap等から発見されなくなったURL」と「HTTPステータスが404を返すURL」は別の概念として区別する（要件定義書 23節の補足）。

| 状況 | 扱い |
|---|---|
| sitemap・クロールどちらからも発見されなくなったURL | manifestから**削除**する（要件定義書 23節の「削除ページ」に該当） |
| 引き続き発見されるが、取得すると404・ROBOTS_DENIEDを返すURL | manifestに**保持**する（`crawl_result` を更新）。次回実行時も再試行する |

## metadata/{page_hash}.json

### 役割

ページ単位の詳細情報を保持する。差分更新では使用せず、以下の処理で利用する。

- Markdown生成
- Index.md生成
- NotebookLM向け出力
- 統計情報

**`metadata/` はクロール結果が `SUCCESS` のページのみ書き込む。**

### 格納形式

```json
{
  "title": "Authentication",
  "url": "https://supabase.com/docs/guides/auth",
  "language": "en",
  "word_count": 1234,
  "char_count": 7890,
  "token_count": 1567,
  "content_sha256": "sha256_of_body",
  "retrieved_at": "2026-06-30T21:30:45+09:00",
  "content_type": "text/html"
}
```

### フィールド

| フィールド | 型 | Nullable | 説明 |
|---|---|---|---|
| `title` | `str` | Yes | trafilaturaが抽出したタイトル。取得できない場合は `null` |
| `url` | `str` | No | 元URL |
| `language` | `str` | Yes | trafilaturaが推定した言語コード。推定できない場合は `null` |
| `word_count` | `int` | No | 単語数 |
| `char_count` | `int` | No | 文字数 |
| `token_count` | `int` | No | tiktokenによる推定トークン数 |
| `content_sha256` | `str` | No | 本文SHA-256 |
| `retrieved_at` | `str` | No | 取得日時（ISO8601 タイムゾーン付き） |
| `content_type` | `str` | No | MIMEタイプ |

> `summary` フィールドは保持しない。Index.md生成時にビルド処理が `pages/{page_hash}.md` の本文先頭から概要を動的に生成する。

---

## pages/{page_hash}.md

### 役割

抽出済みMarkdown本文を保持する。本文のみを保存し、メタ情報は保持しない。

**`metadata/` と同様、クロール結果が `SUCCESS` のページのみ書き込む。**

## chunk_manifest.json

### 役割

NotebookLMへ生成したチャンクと元ページとの対応関係を保持する。重複ページは含めない。

### 格納形式

```json
[
  {
    "title": "Authentication",
    "url": "https://supabase.com/docs/guides/auth",
    "file": "docs_001.md",
    "sha256": "sha256_of_body",
    "word_count": 1234
  }
]
```

## DTO構成

### ConfigRecord

実行時設定を保持する。

### ManifestRecord

`manifest.json` の1ページレコードを表現する。

```python
@dataclass(frozen=True)
class ManifestRecord:
    page_hash: str
    etag: Optional[str]
    last_modified: Optional[str]
    sitemap_lastmod: Optional[str]
    content_sha256: Optional[str]
    last_crawled: datetime          # ISO8601 タイムゾーン付き
    crawl_result: CrawlResult
```

### PageMetadataRecord

`metadata/{page_hash}.json` の1件を表現する。

```python
@dataclass(frozen=True)
class PageMetadataRecord:
    title: Optional[str]
    url: str
    language: Optional[str]
    word_count: int
    char_count: int
    token_count: int
    content_sha256: str
    retrieved_at: datetime          # ISO8601 タイムゾーン付き
    content_type: str
```

### ChunkRecord

`chunk_manifest.json` の1件を表現する。

### BuildResultRecord

ビルド結果を保持する。

### SiteContextRecord

サイト単位の処理状態を保持する。

### CrawlResult（列挙型）

```python
class CrawlResult(str, Enum):
    SUCCESS            = "SUCCESS"
    NOT_MODIFIED       = "NOT_MODIFIED"
    NOT_FOUND          = "NOT_FOUND"
    ROBOTS_DENIED      = "ROBOTS_DENIED"
    NETWORK_ERROR      = "NETWORK_ERROR"
    TIMEOUT            = "TIMEOUT"
    SERVER_ERROR       = "SERVER_ERROR"
    TOO_MANY_REQUESTS  = "TOO_MANY_REQUESTS"
```

## Mapper

### 役割

- DTOとJSONの相互変換を担当する。
- 日時フィールドのISO8601（タイムゾーン付き）シリアライズ／デシリアライズを担う。
- **Mapper以外はJSONを直接操作しない。**

### 配置

```
mapper/
  manifest_mapper.py
  page_metadata_mapper.py
  chunk_mapper.py
```

MapperはDTOごとに配置する。

---

## データフロー

```
JSON
  ↓
Mapper
  ↓
DTO
  ↓
Application
  ↓
DTO
  ↓
Mapper
  ↓
JSON
```

- JSONはMapper層のみが扱う。
- Application層はDTOのみを利用する。

## 重複判定（Builder）

重複判定はmanifestでは行わず、**Builderがビルドのたびに全metadataを照合して都度判定する。**

### 判定ロジック

1. 対象サイトの `metadata/{page_hash}.json` を全件読み込む。
2. `content_sha256` をキーとしてグループ化する。
3. 同一 `content_sha256` を持つページが複数存在する場合、`retrieved_at` が最も新しいページを正として残す（要件定義書18節：後から見つかったURL優先）。
4. それ以外のページは結合Markdown（`docs_XXX.md`）および `chunk_manifest.json` への出力対象から除外する。

### 注意

- 重複として除外されたページは `Index.md` にも含めない。
- 重複判定の結果はビルド実行のたびに再計算されるため、過去の判定結果をキャッシュする必要はない。
